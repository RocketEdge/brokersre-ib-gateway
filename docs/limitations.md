# Limitations

| # | Limitation | What resolves it |
|---|---|---|
| L01 | Partly resolved 2026-11-12. Three patterns in `ibc-patterns.tsv` are confirmed against this image's real IBC output on Gateway 10.50.1g (`ibc_version`, `login_dialog`, `login_failed_dialog`; fixture `tests/fixtures/ibc-real-failed-login.log`), and two were wrong before (the login window is titled "IBKR Gateway"; every dialog is logged three times). The other seven (second factor, login completed, existing session, re-login, daily restart) still come from IBC 3.24.x sources: no login has succeeded on this image yet. | Scrubbed real logs of a successful login, a second-factor prompt, a daily restart and a competing session; extend the real fixtures and adjust the patterns. |
| L02 | Partly resolved 2026-11-12. During login the Gateway writes `.hwid` and `.java/` into the JVM's `user.home` and Mesa writes a shader cache under `$XDG_CACHE_HOME`; with the image home read-only the Gateway blocked behind an unhandled "directory not accessible" dialog (found with a thread dump). `java-env.sh` now points `user.home` at `<settings>/.java-home`, and a login under `read_only: true` reaches authentication. Also seen: the Gateway tries to rename its launcher `ibgateway` to `ibgateway1` in the install directory (fails silently when read-only, no effect observed) and writes `jars/`, `launcher.log` and `loginFailFrequency.txt` into the settings directory. Paths written **after** a successful login are still unknown. | A successful paper login on a read-only container; record any further path. |
| L03 | Partly resolved 2026-11-12: `launcher.log` is confirmed in the settings directory. The dated `ibgateway.*.log` name mirrored by `tail-gateway-logs.sh` is still unverified; the Gateway's per-user logs are written after login and IBKR encrypts them. | A successful paper login; list the settings directory. |
| L04 | Nothing started by a push or a pull request logs in (by design), so a Gateway UI change that breaks IBC's login automation is not caught by CI. A separate, manually dispatched qualification exists (`scripts/qualify-paper.sh`, `qualify-paper.yml`, ADR 0014), but no image has passed it yet (L16) and `stable` does not wait for it. | Recorded passes of the qualification; then move `stable` only after one. |
| L09 | Contract v2 (2026-11-12): the second-factor lines (`twofa_initiated`, `twofa_timeout`), `login_completed`, `relogin_required`, `daily_restart` and therefore the prompt cap `TWOFA_MAX_PROMPTS` rest on the exact text in IBC 3.24.2's source code, not on a real log. If IBC logs something else in practice, the cap does not trigger (the gateway then behaves as without a cap). | A real log of a second-factor prompt, its timeout and a completed login. |
| L10 | `unknown_window` compares window titles with a list taken from IBC's source and one real start. A harmless window that is not on the list raises a false warning; nothing acts on it. | Real sessions over several weeks; extend `known-windows.txt`. |
| L11 | The resource sampler's JVM figures (`java_rss_bytes`, `java_threads`, `open_fds`) and the CLOSE_WAIT count were checked against fixtures and a stand-in process, never against a logged-in Gateway. On a cgroup v1 host the cgroup keys are simply absent. | A real session; a cgroup v1 host. |
| L12 | The relay gate was tested with stand-ins and offline. Its behaviour across a real daily restart (phase `restarting`, then `logged-in` again) has not been observed. | A real session through one daily restart. |
| L13 | `JAVA_HEAP_MB` is verified offline (the Gateway reports a 1024 MB heap when asked for one). The memory a logged-in Gateway needs beyond the heap is not measured, so the 2 GB limit of the compose example is an estimate. | Memory samples of a real session under load. |
| L14 | The preflight compares the restart time with IBKR's reset windows only when `TIME_ZONE` is in one of three families (US Eastern, Central European, UTC+8): the image has no time-zone database. For any other zone the check is skipped and says so. | Adding a zone database to the image (a package, so an ADR), or doing the comparison in a sidecar. |
| L15 | `HEALTHCHECK_API=handshake` and `api-handshake.sh` were tested against stand-in servers only. That a logged-in Gateway answers the handshake every 15 s without side effects (log noise, a dialog, a counted connection) has not been observed, which is why the option is off by default. | A qualification run plus a day of a real session with the option on. |
| L16 | The qualification (`scripts/qualify-paper.sh`, ADR 0014) has run offline only: its failure path is tested, its success path is not, because no login has succeeded on this image yet. It covers a fresh login; the daily restart, the weekly re-authentication and a competing session need longer observation. | A first qualified run with working paper credentials; then a session observed through a daily restart. |
| L05 | arm64 images rely on Ubuntu's `openjdk-25-jre` because IBKR ships no ARM JRE; untested on real hardware. | An arm64 paper login. |
| L06 | IBKR's installer URL is unversioned and unsigned; the SHA-256 is RocketEdge-computed at detection time, so it proves consistency with what RocketEdge saw, not authenticity from IBKR. | IBKR publishing checksums or signatures. |
| L07 | ~~The first `publish.yml` run needs the GHCR package made public by the owner.~~ Resolved 2026-11-01: the owner made the package public; anonymous pull and credential-free `cosign verify` pass. | Resolved. |
| L08 | IB Gateway 10.50.1f and 10.51.1e bundle `jackson-core`/`jackson-databind` 2.12.3 and `commons-io` 2.11.0, which carry fixable HIGH/CRITICAL CVEs. The image cannot replace vendor jars without altering IBKR's application, so the Trivy gate covers OS packages only and vendor-jar findings are printed (not gated) in every CI and publish run. Exposure is limited: the Gateway API listens on loopback, the relay is bound to the private NIC and the Gateway only talks to IBKR. | IBKR shipping updated jars (re-check in every `detect-releases.yml` PR); widen the gate to libraries once the vendor jars are clean. |
