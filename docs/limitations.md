# Limitations

| # | Limitation | What resolves it |
|---|---|---|
| L01 | Partly resolved 2026-11-12. Three patterns in `ibc-patterns.tsv` are confirmed against this image's real IBC output on Gateway 10.50.1g (`ibc_version`, `login_dialog`, `login_failed_dialog`; fixture `tests/fixtures/ibc-real-failed-login.log`), and two were wrong before (the login window is titled "IBKR Gateway"; every dialog is logged three times). The other seven (second factor, login completed, existing session, re-login, daily restart) still come from IBC 3.24.x sources: no login has succeeded on this image yet. | Scrubbed real logs of a successful login, a second-factor prompt, a daily restart and a competing session; extend the real fixtures and adjust the patterns. |
| L02 | Partly resolved 2026-11-12. During login the Gateway writes `.hwid` and `.java/` into the JVM's `user.home` and Mesa writes a shader cache under `$XDG_CACHE_HOME`; with the image home read-only the Gateway blocked behind an unhandled "directory not accessible" dialog (found with a thread dump). `java-env.sh` now points `user.home` at `<settings>/.java-home`, and a login under `read_only: true` reaches authentication. Also seen: the Gateway tries to rename its launcher `ibgateway` to `ibgateway1` in the install directory (fails silently when read-only, no effect observed) and writes `jars/`, `launcher.log` and `loginFailFrequency.txt` into the settings directory. On 2026-11-13 two sessions that IBKR authenticated (they stopped at a `Paper Account Notice`, L31, so no login completed) changed nothing outside the mounts: `docker diff` showed only the mount point of the secrets. Paths written **after** a completed login are still unknown. | A successful paper login on a read-only container; record any further path. |
| L03 | Partly resolved 2026-11-12: `launcher.log` is confirmed in the settings directory. The dated `ibgateway.*.log` name mirrored by `tail-gateway-logs.sh` is still unverified; the Gateway's per-user logs are written after login and IBKR encrypts them. An authenticated session that did not complete its login (2026-11-13) left `launcher.log`, `loginFailFrequency.txt`, `jts.ini`, `jars/locales.jar` and `.java-home/.hwid` in the settings directory and no `ibgateway.*.log`. | A successful paper login; list the settings directory. |
| L04 | Nothing started by a push or a pull request logs in (by design), so a Gateway UI change that breaks IBC's login automation is not caught by CI. A separate, manually dispatched qualification exists (`scripts/qualify-paper.sh`, `qualify-paper.yml`, ADR 0014), but no image has passed it yet (L16) and `stable` does not wait for it. | Recorded passes of the qualification; then move `stable` only after one. |
| L09 | Contract v2 (2026-11-12): the second-factor lines (`twofa_initiated`, `twofa_timeout`), `login_completed`, `relogin_required`, `daily_restart` and therefore the prompt cap `TWOFA_MAX_PROMPTS` rest on the exact text in IBC 3.24.2's source code, not on a real log. If IBC logs something else in practice, the cap does not trigger (the gateway then behaves as without a cap). | A real log of a second-factor prompt, its timeout and a completed login. |
| L10 | `unknown_window` compares window titles with a list taken from IBC's source and one real start. A harmless window that is not on the list raises a false warning; nothing acts on it. The first real case (2026-11-13) was a true one: the dialog `Paper Account Notice` was reported at once, and the login could not continue behind it (L31). | Real sessions over several weeks; extend `known-windows.txt`. |
| L11 | The resource sampler's JVM figures (`java_rss_bytes`, `java_threads`, `open_fds`) and the CLOSE_WAIT count were checked against fixtures and a stand-in process, never against a logged-in Gateway. On a cgroup v1 host the cgroup keys are simply absent. | A real session; a cgroup v1 host. |
| L12 | The relay gate was tested with stand-ins and offline. Its behaviour across a real daily restart (phase `restarting`, then `logged-in` again) has not been observed. | A real session through one daily restart. |
| L13 | `JAVA_HEAP_MB` is verified offline (the Gateway reports a 1024 MB heap when asked for one). The memory a logged-in Gateway needs beyond the heap is not measured, so the 2 GB limit of the compose example is an estimate. | Memory samples of a real session under load. |
| L14 | The preflight compares the restart time with IBKR's reset windows only when `TIME_ZONE` is in one of three families (US Eastern, Central European, UTC+8): the image has no time-zone database. For any other zone the check is skipped and says so. | Adding a zone database to the image (a package, so an ADR), or doing the comparison in a sidecar. |
| L15 | `HEALTHCHECK_API=handshake` and `api-handshake.sh` were tested against stand-in servers only. That a logged-in Gateway answers the handshake every 15 s without side effects (log noise, a dialog, a counted connection) has not been observed, which is why the option is off by default. | A qualification run plus a day of a real session with the option on. |
| L16 | The qualification (`scripts/qualify-paper.sh`, ADR 0014) has not passed yet. It ran against IBKR for the first time on 2026-11-13, on the published stable image, with credentials IBKR accepted, and ended "not qualified" for a reason on the account's side: the account has no paper trading access, so the login stopped at a `Paper Account Notice` (L31). That exercised the failure path for real: one attempt, `unknown_window` reported, the time limit, a stop that completed in 2 seconds (`shutdown_complete`), `result.json`. The success path is still untested. It covers a fresh login; the daily restart, the weekly re-authentication and a competing session need longer observation. | A paper trading account that IBKR has enabled; then a first qualified run and a session observed through a daily restart. |
| L17 | `RELAY_ALLOW_CIDR` judges the peer address the relay sees. Through a published port on Docker Desktop that is the bridge gateway (`172.17.0.1` in the test of 2026-11-12), not the client, so the allowlist cannot separate host-side clients there; what Docker Engine on Linux shows for a remote client was not measured. It takes one IPv4 network (socat ignores a second `range`), and IPv6 peers are not served by the relay at all. | Measure the peer address on Docker Engine with a remote client; an allowlist of several networks would need another relay than socat. |
| L18 | The rejected-login latch (ADR 0016) is keyed on the modification times of the secret files and stored on the log volume. It does not survive a re-created container without a persistent log volume; credentials passed as plain variables stay held until `LOGIN_LATCH=clear`; a secret restored with its old modification time stays held, and one rewritten with the same wrong password gets one more attempt; secrets on a tmpfs that is rebuilt per container get a new time with every container. Only IBKR's "Unrecognized Username or Password" dialog sets it: whether an expired password, a locked account or a disabled user shows another dialog is unknown. Tested with the real rejected-login log as a fixture and offline in the container suite, never across a real password change at IBKR. | A real log of each other rejection; one observed cycle of rejection, correction and login. |
| L19 | The Azure Log Analytics pack (`azure/`, ADR 0012) has never been deployed. Proven offline: the templates compile, the shipper maps and redacts lines of a real gateway run, the rows match the declared schema, the queries type-check. Unproven: ingestion and authentication (managed identity and certificate), the role assignments taking effect, the three alert rules firing (their logic was type-checked, not executed), the workbook and query pack in the portal, the deployment-time refusals, and everything about the optional VM (first boot, `apply-config.sh` on a real VM, restart behaviour). Delivery is at least once; an account id written without its prefix or glued to a digit or upper-case letter is not redacted in raw logs (which are off by default). | One deployment to a test subscription with a gateway shipping for a day; one run of each alert rule's condition. |
| L20 | The optional sidecar (`sidecar/`, ADR 0010) has not run against a logged-in Gateway. Unproven: the API handshake and the time request through the relay against a real Gateway, the 20 s grace after `login_completed` against the relay's real start-up time, the wording of notices 1100, 1101, 1102 and of the farm codes, error 326 for a client id in use, the second-factor timeline with a real prompt, and the clock offset against IBKR's answer. The notification channels were checked against local receivers, not the real services. Its three workflows have not run. | A paper login with the sidecar attached; one test message per channel to the real service; the first workflow runs. |
| L21 | What the sidecar cannot tell anyone: a dead host is silent unless the dead-man ping is configured and watched from outside; a killed gateway is announced after five minutes of silence, not at once; in the shared-namespace mode a stopped gateway cannot be reported at all (the sidecar loses its network with it). Its table of IBKR reset windows was taken from IBKR's status page as quoted by search results on 2026-11-12; the page refused an automated fetch. | A dead-man check on every deployment; a person reading IBKR's system status page once. |
| L05 | arm64 images rely on Ubuntu's `openjdk-25-jre` because IBKR ships no ARM JRE, and no arm64 image has completed a login on real hardware. The arm64 image is scanned: `publish.yml` runs the same Trivy gate on `linux/arm64` as on `linux/amd64`, on the digest it is about to tag, before any tag moves. Images published up to 2026-11-11 were gated on amd64 only; a manual scan of both platforms of those digests on 2026-11-12 found no CRITICAL or HIGH finding with a fixed package in OS packages. CI (`ci.yml`) still builds and tests amd64 only. | An arm64 paper login. |
| L06 | IBKR's installer URL is unversioned and unsigned; the SHA-256 is RocketEdge-computed at detection time, so it proves consistency with what RocketEdge saw, not authenticity from IBKR. | IBKR publishing checksums or signatures. |
| L07 | ~~The first `publish.yml` run needs the GHCR package made public by the owner.~~ Resolved 2026-11-01: the owner made the package public; anonymous pull and credential-free `cosign verify` pass. | Resolved. |
| L08 | IB Gateway bundles third-party jars with known CVEs, and the image cannot replace them without altering IBKR's application. On 10.50.1g and 10.51.1e Trivy reports 25 CVEs (12 HIGH, 13 MEDIUM on 2026-11-12) in `jackson-core`/`jackson-databind` 2.12.3, `commons-io` 2.11.0 and `log4j-api`/`log4j-core` 2.25.3. The Trivy gate therefore covers OS packages only. The project's position on each CVE is [`security/vex/ibgateway-vendor-jars.openvex.json`](../security/vex/ibgateway-vendor-jars.openvex.json) (OpenVEX): every statement is `under_investigation`, because whether the Gateway can reach the vulnerable code is known to IBKR, not to this project; each statement says what triggers the CVE and what is unknown. `scripts/check-vex.sh` compares the document with Trivy's findings in every CI and publish run and warns about a CVE without a statement or a statement without a CVE (a warning, not a gate). A change to the document reaches an image's attestation only at its next publish. What bounds the exposure without proving that there is none: the Gateway API listens on loopback and the relay is published on loopback or a private address. | IBKR shipping updated jars, or stating which of the CVEs apply (the drift check names what changed on every Gateway version bump); widen the gate to libraries once the vendor jars are clean. |
| L22 | `/usr/bin/pebble` of the Ubuntu base image is a Go binary owned by no package; Trivy reports a Go standard-library CVE in it. The OS gate does not cover it and `apt-get upgrade` cannot replace it. Nothing in the image starts it. | A base image digest with a rebuilt pebble, or removing the binary in a change of its own, proven by a real login. |
| L23 | A publish whose gate fails leaves an untagged, unsigned image index and its platform manifests in the registry. The daily rebuild stops requesting after `REBUILD_MAX_ATTEMPTS` days (default 3), which bounds this per incident. | A cleanup that deletes the index and exactly its own manifests, tested against the registry's package API. |
| L24 | The schedule that scans the published images is best effort: GitHub may delay or drop a scheduled run and disables schedules after 60 days without repository activity. The reworked `publish.yml` and `rebuild.yml` have not run on GitHub yet: they run only from `main`, so the merge is their first run. | An external monitor of the last scan run, or regular repository activity; the first runs, recorded in `docs/changes.md`. |
| L25 | Partly resolved 2026-11-13. On a real Gateway the automatic screenshot was saved 33 ms after `unknown_window`. That file was deleted without being looked at, because a picture taken that early can show the login window with the username in it; whether it shows the dialog completely drawn is therefore not established. A second picture, taken on request 12 seconds later, showed the blocking dialog with its whole text and its one button: it named the cause (the account has no paper trading access), which the title `Paper Account Notice` alone did not. The file is XWD with 16 bits per pixel (the virtual screen has depth 16), which needs GIMP, ImageMagick or `xwud` to open (the image has no converter and gets none). A copy taken while the screen is redrawn can show a half-drawn window. The picture can show the username and account information, which is why the option is off by default. | The automatic picture of a real blocking dialog looked at (is the window drawn after 33 ms, or should the picture be taken a moment later?); a real login window looked at; a decision whether the default can change. |
| L26 | The break-glass console (ADR 0017) was tested offline only: the image's real x11vnc and a client written in bash standing in for a viewer. Not observed: the console during a real login, the SSH tunnel, a desktop VNC viewer. Switching it on, or from view-only to input, recreates the container and starts a new login, so a window seen view-only cannot be answered in the same session. x11vnc has no idle limit. A connection that never authenticated is not an event, and a session open at shutdown has no `vnc_client_disconnected`. While the bridge runs, containers on the same Docker network can reach port 5901 behind the VNC password (eight characters at most). | An attended paper login with the console; a decision on a run-time switch for input with an event of its own; a bridge limited to the Docker host. |
| L27 | `scripts/check-upgrade.sh` was tested with a stand-in `docker` and by hand against other projects' public images, not against this repository's registry, a private registry or a mirror. A differing digest is reported as "upgrade available" without judging which of the two is newer. | A run against the published image; a run with a mirror and `--repository`. |
| L28 | The recipes in `docs/recipes/` were validated with `vector validate` and against stand-in receivers only (Vector's own OTLP receiver; for Loki and Datadog an HTTP server that accepts the request). Delivery to a real Loki, collector or Datadog, their limits, TLS and a long outage are untested. Resource samples are shipped as logs, and the first start ships every kept generation. | One recipe run against a real system for a week. |
| L29 | Whether IB Gateway accepts a passkey, and what that would need on Linux, is not established: IBKR lists TWS (10.46.1d) for passkey login and not IB Gateway, and nothing was tested (`docs/passkeys.md`). | A statement from IBKR, or an attended paper login with a passkey-enrolled account. |
| L30 | `publish.yml` moves a channel's tags and writes its GitHub release afterwards; the two cannot be one step. The release step repeats itself five times over about two and a half minutes (`scripts/release-upsert.sh`). If GitHub fails for longer, the job ends with the tags on the new digest and the release not rewritten: its notes still name the previous digest, and some of its assets (`digests-<channel>.json`, the SBOMs) can be missing, because replacing an asset deletes the old one first. Both digests are scanned and signed images. Nothing repairs that by itself. The script's use of `gh` was checked with gh 2.81.0 against a local stand-in for the API, not against GitHub: in particular that a draft left by a failed creation is found by its tag. | Re-run the failed job (`gh run rerun <id> --failed`): it rebuilds, moves the tags to the rebuilt digest and writes the release. A check that compares tag and release after every publish would make the state visible without reading the log. |
| L31 | A login in paper mode with an account that has no paper trading access is authenticated by IBKR and then stops at the dialog `Paper Account Notice` ("This account does not have paper trading access enabled. Please log into Account Management to request access.", one button `OK`; seen with 10.50.1g on 2026-11-13). IBC has no handler for it and nothing in the image clicks it away. The gateway reports `unknown_window` at once and `login_stalled` after `LOGIN_STALL_S`, but the phase stays `login`, not `needs-human`, and no event names the cause: it is in the dialog's text, which only a screenshot (`SCREENSHOTS=yes`) or IBC's window-structure log shows. Whether IBKR uses the same title for other notices is not known. | A decision on classifying the dialog (by its title, or by its text once IBC's structure log is read): phase `needs-human` and an event of its own, with the sidecar's cause list and the runbooks. |
